This setup is much closer to a real production deployment than the earlier versions, but it is still missing some important features before it could safely handle real customer traffic.

For external routing, the system currently uses an Ingress controller to route traffic to the kk-api and kk-payments services. This works well for organising traffic through a single entry point, but all traffic is still using plain HTTP. Since kk-payments would handle sensitive payment information, this creates a security risk because data could potentially be intercepted while travelling across the network. In a production environment, TLS should be enabled at the Ingress layer so traffic is encrypted using HTTPS. This could be done by adding a TLS section to the Ingress resource and using cert-manager to manage certificates automatically. Another important improvement would be rate limiting to reduce abuse or denial-of-service attacks. NGINX Ingress annotations can be used to limit how many requests a client can send within a certain time period.

The readiness and liveness probes are useful because they help Kubernetes detect when a container is healthy and ready to receive traffic. However, the current timing values are still basic defaults and would need adjustment for a real payment service. If the application takes longer to connect to the database during startup, the probes may fail too early and Kubernetes could restart a container that would have recovered on its own. A failureThreshold that is too low could also cause unnecessary restarts during temporary database slowdowns or heavy traffic periods. For a payments system, unnecessary restarts are risky because they may interrupt transactions or reduce availability during busy periods.

The deployment currently uses three kk-payments replicas and two kk-api replicas, which improves availability compared to a single container. However, scaling is still manual. A real production system would require Horizontal Pod Autoscaling so the cluster can automatically increase or decrease the number of Pods based on CPU or memory usage. This would require the metrics-server to be installed and accurate resource requests configured in the manifests. If the autoscaling target CPU percentage is set too high, scaling will happen too late and users may experience slow responses under heavy load. If the target is set too low, the system may create too many Pods unnecessarily, wasting resources and increasing infrastructure costs.

Overall, the current deployment is stable enough for development and testing, but production use would still require stronger security, smarter scaling, and more carefully tuned health monitoring before it could safely support real KijaniKiosk customers.
